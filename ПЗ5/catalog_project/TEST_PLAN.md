# ПЗ5. Проект каталога: представления и тестирование

## Что нужно было сделать по методичке

Практическая работа 5 относится к этапу проверки отображения каталога. В этой работе нужно не разрабатывать формы создания, редактирования и удаления, а доработать вывод каталога и покрыть его тестами.

По методичке требовалось:

- доработать список товаров, чтобы его можно было сортировать не только по алфавиту;
- добавить сортировку по другому обязательному полю;
- добавить сортировку по необязательному полю;
- добавить сортировку или группировку по полю типа товара;
- добавить возможность показать группу товаров через GET-параметр, например `?type=...`;
- перенести тесты в пакет `catalog/tests`;
- разделить тесты на `test_routes.py` и `test_content.py`;
- разработать файл `TEST_PLAN.md` с 9 обязательными разделами;
- сделать матрицу минимум из 10 тест-кейсов;
- проверить только GET-запросы, маршруты, шаблоны, контекст, фильтрацию, сортировку и страницу About;
- не тестировать авторизацию, POST-запросы, формы создания/редактирования и API.

## Как вообще работает ПЗ5

Проект `ПЗ5/catalog_project` - это Django-приложение каталога аккумуляторов. Главная страница показывает список товаров, позволяет искать аккумуляторы, фильтровать их по типу и наличию, а также сортировать по нескольким полям.

Основные файлы проекта:

- `catalog/models.py` - модели данных;
- `catalog/views.py` - функции представлений;
- `catalog/urls.py` - маршруты приложения;
- `catalog/templates/catalog/product_list.html` - страница списка товаров;
- `catalog/templates/catalog/product_detail.html` - страница одного товара;
- `catalog/templates/catalog/about.html` - статическая страница о магазине;
- `catalog/tests/test_routes.py` - тесты маршрутов и статус-кодов;
- `catalog/tests/test_content.py` - тесты контента, фильтрации и сортировки.

В проекте есть две основные модели:

- `BatteryType` хранит тип аккумулятора: автомобильный, power bank, AA/AAA, ИБП и т.д.
- `Battery` хранит сам товар: артикул, название, бренд, тип, емкость, напряжение, цену, остаток на складе, гарантию и дополнительные характеристики.

Главная view-функция `product_list` получает GET-параметры:

- `q` - строка поиска по названию, бренду, артикулу и описанию;
- `type` - фильтр по типу аккумулятора;
- `availability` - фильтр по наличию;
- `sort` - выбранный способ сортировки.

После обработки параметров view передает в шаблон:

- `products` - найденные товары;
- `battery_types` - список типов аккумуляторов для выпадающего фильтра;
- выбранные значения фильтров;
- список доступных вариантов сортировки.

Страница `/product/<pk>/` открывает карточку конкретного товара. Если товара с таким `pk` нет, Django возвращает `404`. Страница `/about/` является обычной статической страницей, которую тоже нужно было покрыть тестами по методичке.

# Introduction

Тест-план описывает проверку модуля отображения каталога аккумуляторов в практической работе 5. Цель проверки - убедиться, что страницы каталога открываются через правильные маршруты, используют нужные шаблоны, передают корректный контекст и правильно обрабатывают GET-параметры поиска, фильтрации и сортировки.

Работа выполняется в рамках этапа "Проект каталог. Тесты представлений", поэтому основное внимание уделяется view-функциям и содержимому страниц, а не изменению данных.

# Test Items

Проверяемые view-функции:

- `product_list` - главная страница каталога;
- `product_detail` - детальная страница товара;
- `about` - статическая страница о магазине.

Проверяемые URL:

- `/` - список товаров;
- `/product/<pk>/` - карточка товара;
- `/about/` - страница About.

Проверяемые тестовые файлы:

- `catalog/tests/test_routes.py`;
- `catalog/tests/test_content.py`.

# Features to be tested

Проверяются следующие возможности:

- доступность маршрутов и связь URL с нужными view-функциями;
- статус-коды GET-запросов `200` и `404`;
- загрузка ожидаемых HTML-шаблонов;
- наличие нужных ключей в `response.context`;
- вывод товаров, созданных в `setUpTestData`;
- поиск товара через GET-параметр `q`;
- фильтрация товаров по типу аккумулятора через GET-параметр `type`;
- фильтрация по наличию через GET-параметр `availability`;
- сортировка по названию;
- сортировка по обязательному полю `price`;
- сортировка по необязательному полю `weight_grams`;
- сортировка по полю типа `battery_type`;
- обработка неверного значения сортировки;
- корректный вывод пустого списка;
- отображение статической страницы About.

# Features NOT to be tested

- формы редактирования товара;
- формы удаления товара;

- API;
- работа Django admin;
- бизнес-правила моделей, которые относятся к предыдущим практическим работам.

# Approach

Тестирование выполняется стандартными средствами Django:

- `django.test.TestCase` используется как базовый класс тестов;
- `django.test.Client` выполняет GET-запросы к страницам;
- `setUpTestData` создает тестовые типы аккумуляторов и товары;
- `reverse()` используется для построения URL по имени маршрута;
- `resolve()` используется для проверки связи URL с view-функцией;
- `assertTemplateUsed()` проверяет, какой шаблон был загружен;
- `assertContains()` и `assertNotContains()` проверяют текст на странице;
- `response.context` проверяется как словарь с данными, переданными в шаблон.

Тесты разделены по назначению:

- `test_routes.py` проверяет маршруты, reverse, resolve, GET-статусы и 404;
- `test_content.py` проверяет шаблоны, контекст, список товаров, поиск, фильтрацию, сортировку и About.

# Item Pass/Fail Criteria

Тест считается пройденным, если выполняются все ожидаемые условия:

- страница возвращает правильный HTTP-статус;
- URL ведет к нужной view-функции;
- используется правильный шаблон;
- контекст содержит нужные ключи;
- список товаров содержит ожидаемые объекты;
- фильтрация оставляет только подходящие товары;
- сортировка возвращает товары в ожидаемом порядке;
- для несуществующего товара возвращается `404`;
- About открывается и содержит ожидаемый текст.

Тест считается проваленным, если маршрут не найден, возвращается неправильный статус, загружается неверный шаблон, в контексте нет нужных данных или результат фильтрации/сортировки не совпадает с ожидаемым.

# Suspension Criteria

Тестирование нужно приостановить, если:

- падает больше 30% тестов;
- не создается тестовая база данных;
- не применяются миграции;
- тестовые данные не создаются в `setUpTestData`;
- приложение не запускается из-за ошибки конфигурации Django.
