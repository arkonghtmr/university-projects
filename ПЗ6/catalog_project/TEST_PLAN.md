# ПЗ6. Проект каталога: формы, роли и работа с данными

## Что нужно было сделать по методичке

Практическая работа 6 продолжает проект каталога и переводит его от простого просмотра товаров к работе с данными. Если в ПЗ5 проверялись представления каталога, то в ПЗ6 нужно добавить роли пользователей, формы изменения товаров и механизм формирования партии товара на отправку.

По методичке требовалось:

- добавить несколько ролей пользователей;
- сделать так, чтобы администратор мог выполнять все операции;
- сделать роль товароведа, который может работать с описанием товара через интерфейс каталога;
- сделать роль менеджера по продажам, который может формировать партию товара на отправку;
- оставить гостю только просмотр каталога;
- добавить в товар цену за единицу;
- добавить цену или скидку для мелкого опта;
- добавить цену или скидку для крупного опта;
- добавить количество, с которого начинается мелкий и крупный опт;
- добавить корзину или аналогичный механизм, где формируется партия товара на отправку;
- добавить расчет суммы партии с учетом оптовых цен;
- добавить дополнительную скидку на общую сумму заказа;
- покрыть новый функционал тестами;
- проверить, что гость может только просматривать;
- проверить разграничение прав по ролям;
- проверить корректное изменение объектов каталога;
- проверить корректный расчет суммы партии;
- учесть, что пользователей с одной ролью может быть несколько;
- запретить одному менеджеру изменять партию, созданную другим менеджером.

В отчете по методичке должны быть исходный код, скриншоты страниц и перечень тестов со словесным описанием проверок.

## Как вообще работает ПЗ6

Проект `ПЗ6/catalog_project` - это Django-приложение каталога аккумуляторов, расширенное формами и ролями. В нем остался каталог из ПЗ5: список товаров, поиск, фильтрация, сортировка, карточка товара и страница About. Дополнительно появились управление товарами и партии на отправку.

Основные файлы проекта:

- `catalog/models.py` - модели товаров, типов аккумуляторов, партий и позиций партий;
- `catalog/forms.py` - формы товара, партии и позиции партии;
- `catalog/views.py` - представления каталога, CRUD товара и работы с партиями;
- `catalog/urls.py` - маршруты каталога, форм и партий;
- `catalog/templates/catalog/product_form.html` - форма создания и редактирования товара;
- `catalog/templates/catalog/product_confirm_delete.html` - подтверждение удаления товара;
- `catalog/templates/catalog/shipment_list.html` - список партий;
- `catalog/templates/catalog/shipment_detail.html` - карточка партии с добавлением товаров и расчетом суммы;
- `catalog/tests/test_routes.py` - тесты маршрутов;
- `catalog/tests/test_content.py` - тесты отображения каталога;
- `catalog/tests/test_forms.py` - тесты формы товара;
- `catalog/tests/test_roles_and_shipments.py` - тесты ролей, прав доступа и партий.

В проекте используются четыре уровня доступа:

- гость не авторизован и может только просматривать каталог, карточки товаров и About;
- товаровед входит в группу `Товароведы` и может создавать, редактировать и удалять товары;
- менеджер продаж входит в группу `Менеджеры продаж` и может создавать партии на отправку, добавлять в них товары и менять скидку;
- администратор определяется через `is_superuser` и имеет доступ ко всем операциям.

Роли проверяются во view-функциях через вспомогательные функции:

- `is_product_specialist(user)` проверяет товароведа или администратора;
- `is_sales_manager(user)` проверяет менеджера продаж или администратора;
- `role_required(...)` закрывает view от гостей и пользователей без нужной роли;
- `role_context(request)` передает в шаблоны признаки `can_manage_products` и `can_manage_shipments`, чтобы показывать нужные кнопки в интерфейсе.

## Как работает товар

Модель `Battery` хранит обычные характеристики аккумулятора и новые поля для опта:

- `price` - цена за одну единицу;
- `small_wholesale_price` - цена мелкого опта;
- `small_wholesale_min_quantity` - количество для мелкого опта;
- `large_wholesale_price` - цена крупного опта;
- `large_wholesale_min_quantity` - количество для крупного опта.

Метод `get_price_for_quantity(quantity)` выбирает цену по количеству:

- если количество достигло порога крупного опта, берется `large_wholesale_price`;
- иначе, если количество достигло порога мелкого опта, берется `small_wholesale_price`;
- иначе используется обычная `price`.

Форма `BatteryForm` проверяет бизнес-правила:

- цена мелкого опта не должна быть выше цены за единицу;
- цена крупного опта не должна быть выше цены мелкого опта;
- порог крупного опта должен быть больше порога мелкого опта;
- артикул `sku` должен быть уникальным.

## Как работает партия на отправку

Модель `Shipment` играет роль корзины или партии товара на отправку. У нее есть владелец `owner`, название партии и дополнительная скидка `additional_discount_percent`.

В партии есть позиции `ShipmentItem`. Каждая позиция хранит товар и количество. Для позиции рассчитываются:

- `unit_price` - цена единицы товара с учетом количества и оптовых правил;
- `total_price` - цена позиции как `unit_price * quantity`.

Для всей партии рассчитываются:

- `subtotal` - сумма всех позиций до дополнительной скидки;
- `discount_amount` - сумма дополнительной скидки;
- `total` - итоговая сумма после скидки.

Менеджер видит и изменяет только свои партии. Если другой менеджер пытается открыть, изменить или удалить позицию чужой партии, приложение возвращает `403 Forbidden`. Администратор может открывать партии всех менеджеров.

# Approach

Тестирование выполняется стандартными средствами Django:

- `django.test.TestCase` используется как базовый класс;
- `django.test.Client` выполняет GET- и POST-запросы;
- тестовые пользователи создаются через Django user model;
- роли создаются через `Group`;
- товароведы помещаются в группу `Товароведы`;
- менеджеры продаж помещаются в группу `Менеджеры продаж`;
- администратор создается как `is_superuser=True`;
- тестовые товары и типы аккумуляторов создаются в `setUpTestData` или через helper-функции;
- `reverse()` проверяет имена маршрутов;
- `resolve()` проверяет связь URL с view;
- POST-запросы проверяют реальные изменения объектов в тестовой базе;
- расчеты партий проверяются напрямую через свойства моделей `subtotal`, `discount_amount` и `total`.

Тесты разделены по назначению:

- `test_routes.py` проверяет маршруты и базовые статусы;
- `test_content.py` проверяет отображение каталога из ПЗ5;
- `test_forms.py` проверяет валидацию и сохранение `BatteryForm`;
- `test_roles_and_shipments.py` проверяет права доступа, роли, CRUD товара и партии на отправку.

# Item Pass/Fail Criteria

Тест считается пройденным, если выполняются ожидаемые условия:

- пользователь с разрешенной ролью получает доступ к операции;
- пользователь без нужной роли получает `403` или redirect на страницу входа;
- гость может только просматривать публичные страницы;
- после POST-запроса нужный объект создается, изменяется или удаляется;
- менеджер видит только свои партии;
- чужая партия недоступна другому менеджеру;
- администратор получает доступ к операциям управления;
- форма товара принимает корректные данные;
- форма товара возвращает ошибки для некорректных цен, порогов и дубля артикула;
- сумма партии совпадает с ручным расчетом по оптовым ценам;
- дополнительная скидка корректно уменьшает итоговую сумму.

Тест считается проваленным, если пользователь получает лишние права, разрешенная операция недоступна, объект после POST не изменяется, форма пропускает некорректные данные или расчет партии не совпадает с ожидаемым.

# Suspension Criteria

Тестирование нужно приостановить, если:

- не создается тестовая база данных;
- не применяются миграции;
- не создаются пользователи или группы ролей;

- невозможно создать базовые тестовые товары и типы аккумуляторов.
